deploy-pr · explained like you're five

How GitHub Actions safely uses AWS without storing a single password

There is a magic trick called OIDC. It lets your GitHub workflow walk into your AWS account, do its job, and walk out — without you ever giving it a key. This page explains how, step by step, with pictures.

0The big idea

Imagine your AWS account is a theme park. To get inside, you need a wristband. There are two ways to give your friend GitHub a wristband:

The old way

Hand GitHub a permanent wristband

You store an AWS access key in a GitHub secret. GitHub keeps it forever. If anyone ever leaks that key, a stranger has a free pass to your park.

The OIDC way

Let GitHub ask for a one-day wristband each time

GitHub shows its own GitHub-issued ID badge at the gate. AWS checks the badge, and if it likes it, hands over a wristband that self-destructs in ~1 hour.

The bouncer analogy

OIDC is a bouncer at the front door of AWS. GitHub walks up and says "hi, I'm the workflow for repo OWNER/REPO, running on a pull_request event." The bouncer checks the signature on that statement (GitHub really did sign it), checks the guest list (your trust policy), and only then waves them through. No keys change hands.

★The whole flow on one page

Before we get into commands, here's the trip a GitHub Action takes when a PR opens:

Six conversations. No secret ever stored in GitHub.

The two pieces of paperwork In step 3, AWS asks two questions before handing over keys: "is this token signed by someone I trust?" (that's the OIDC provider from step 1) and "does the role allow this exact GitHub workflow to assume it?" (that's the trust policy from step 2).

1Tell AWS it trusts GitHub

AWS doesn't know GitHub's signature out of the box. You introduce them once, per AWS account, by creating an OIDC identity provider entry that points at GitHub's token issuer.

Think of it like…

Adding GitHub to the address book of trusted ID-issuers your bouncer accepts. After this, the bouncer recognizes any badge GitHub signs — but recognizing the issuer doesn't mean letting them in. That's step 2's job.

aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com \
  --thumbprint-list 6938fd4d98bab03faadb97b34396831e3780aea1

If you already did this for another project, you can skip it. Check with aws iam list-open-id-connect-providers.

2Make a role (the costume)

A role in AWS is like a costume hanging on a rack. Anyone who matches the rules can put it on, and while they wear it, they get the powers stitched into it.

Two pieces of paper come with every costume:

🔐 Trust policy

Who is allowed to wear this costume?

In our case: only GitHub Actions, running in this specific repo, on a pull_request event.

⚡ Permission policy

What powers does the costume give you?

In our case: push images to one ECR repo, describe one EKS cluster. That's it.

Trust policy = the door. Permission policy = what's inside the room.

⚠️ Don't wildcard the subject A trust policy that allows repo:owner/*:* means any workflow in any of your repos — including a fork that someone opens a malicious PR from — can assume the role. Pin it to one repo and the event you actually want (pull_request, push on main, etc.).

What the two policies look like

// trust-policy.json — who can wear the costume
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::000000000000:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
      "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:OWNER/REPO:pull_request" }
    }
  }]
}

// deploy-pr-policy.json — what the costume can do
// (ECR push on one repo, EKS describe on one cluster, nothing else)

aws iam create-role \
  --role-name github-deploy-pr \
  --assume-role-policy-document file://trust-policy.json

aws iam put-role-policy \
  --role-name github-deploy-pr \
  --policy-name deploy-pr-permissions \
  --policy-document file://deploy-pr-policy.json

The ARN that comes out — something like arn:aws:iam::000000000000:role/github-deploy-pr — is what you paste into your workflow's AWS_ROLE_ARN.

3Let the role into the cluster

Surprise twist: being allowed to describe an EKS cluster isn't the same as being allowed to do things inside it. Kubernetes has its own permission system, sitting behind AWS's.

AWS IAM gets you through the front door. Kubernetes RBAC decides which rooms inside are yours.

To bridge the two, you create an EKS access entry — a row that says "this AWS principal maps to this Kubernetes identity" — and associate a Kubernetes policy with it:

aws eks create-access-entry \
  --cluster-name dev-cluster \
  --principal-arn arn:aws:iam::000000000000:role/github-deploy-pr \
  --type STANDARD

aws eks associate-access-policy \
  --cluster-name dev-cluster \
  --principal-arn arn:aws:iam::000000000000:role/github-deploy-pr \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSEditPolicy \
  --access-scope type=cluster
Quick & loose vs. production AmazonEKSEditPolicy at type=cluster scope is the easy starting point — it lets the role edit basically everything cluster-wide. For real production, swap that scope to type=namespace,namespaces=pr-* so the role can only touch preview namespaces. But that tighter scope has one gotcha — it can't create namespaces. That's what step 4 fixes.

4Let the role create namespaces

First time wondering why this step exists? Pushing images, creating Deployments, mounting Secrets — none of those need extra work. But creating the namespace itself does. The reason is structural, not arbitrary: namespaces are cluster-scoped resources, so they can't be sandboxed to pr-* by RBAC alone. See kubernetes-namespaces-eli5.html for the full mental model.

deploy-pr up defaults to --create-namespace, which asks Helm to create a fresh pr-<N> namespace for each PR. Namespaces are cluster-scoped resources, so a strictly namespace-scoped principal will hit:

namespaces is forbidden: User "..." cannot create resource "namespaces"
  in API group "" at the cluster scope

You have two options. Pick one based on how paranoid your environment is:

Path A · easy

Grant cluster-scoped namespace verbs

Map the principal to a Kubernetes group, then bind a ClusterRole that allows create/get/list/patch/delete on namespaces. Keep --create-namespace on. Works for laptops and CI alike.

Path B · strict

Pre-create namespaces, then run with --create-namespace=false

An admin (or a separate controller) creates pr-<N> ahead of time. The role stays strictly namespace-scoped — no cluster verbs at all. Tighter, but you need something to create the namespace first.

Path A in one snippet

aws eks create-access-entry \
  --cluster-name dev-cluster \
  --principal-arn arn:aws:iam::000000000000:role/github-deploy-pr \
  --kubernetes-groups deploy-pr \
  --type STANDARD

# deploy-pr-rbac.yaml — applied by a cluster admin once
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata: { name: deploy-pr-namespace-manager }
rules:
  - apiGroups: [""]
    resources: ["namespaces"]
    verbs: ["create", "get", "list", "patch", "delete"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata: { name: deploy-pr-namespace-manager }
subjects:
  - { kind: Group, name: deploy-pr, apiGroup: rbac.authorization.k8s.io }
roleRef:
  kind: ClusterRole
  name: deploy-pr-namespace-manager
  apiGroup: rbac.authorization.k8s.io
Caveat about RBAC Kubernetes RBAC can't restrict create by name pattern. This binding grants creation of any namespace, not just pr-*. If that matters, layer a ValidatingAdmissionPolicy (or Kyverno/OPA) that rejects creates from this group whose name doesn't match pr-*.

Path B in one snippet

kubectl create namespace pr-123
kubectl label namespace pr-123 app.kubernetes.io/managed-by=deploy-pr

# Then in CI:
deploy-pr up 123 --create-namespace=false

5Verify it actually works

Open a draft PR. Watch the PR preview workflow in the Actions tab. The first run will fail in interesting places — missing wildcard DNS, ingress class mismatch, image-pull secret missing. That's normal. The CLI's logs name the failing system. Fix forward, don't rip and replace.

You're done when… A PR opens → workflow runs → temp credentials get assumed → image gets pushed to ECR → Helm install lands in pr-<N> → the bot posts a preview URL on the PR. No long-lived AWS keys exist anywhere in your repo settings.

★Operational tips

  • ECR storage cost. Every PR build pushes a new image. Without a lifecycle policy your ECR repo grows forever. Set one to expire untagged images after 30 days, and to keep only the latest N tags per PR.
  • Orphan namespaces. If the close workflow fails to run (runner queue full, branch deleted weirdly), the namespace gets stuck. deploy-pr list will flag it as orphaned. Run deploy-pr down <PR> from a laptop to clean it up.
  • Drift between laptop and CI. The same binary runs in both places, so a developer's local deploy-pr up <PR> can overwrite the CI-deployed release for that PR. For ephemeral previews that's fine — if it isn't, scope IAM so laptop credentials lack push privileges.
