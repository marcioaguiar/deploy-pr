What a Kubernetes namespace is — and why creating one is the privileged part

A namespace is a folder inside a Kubernetes cluster. Once you see it that way, the asymmetry in deploy-pr's permissions stops being surprising: putting files into a folder is one kind of permission, creating a new folder at the root of the disk is a completely different one.

1The folder analogy

Imagine your Kubernetes cluster is a single filesystem. The cluster is the disk. Most of the things you create — Deployments, Pods, Services, Secrets, ConfigMaps, Ingresses — are files. And namespaces are folders that group those files.

Mental model

Cluster = the disk. Namespace = a folder at the root of the disk. Deployment / Pod / Service / Secret = files inside that folder. Different folders can hold files with the same name — pr-123/api and pr-456/api coexist peacefully, just like ~/work/notes.md and ~/personal/notes.md.

One cluster, several namespaces. Same object name (api) can exist in each, because the folder makes it unique.

2What a namespace actually does for you

A namespace isn't just a label — it changes how five different Kubernetes systems treat the objects inside it.

naming

Names only need to be unique per folder

You can have a Service called api in pr-123 and another in pr-456. Their DNS names become api.pr-123.svc.cluster.local and api.pr-456.svc.cluster.local. This is exactly how deploy-pr can spin up N PR previews of the same Helm chart without name collisions.

RBAC

Most permissions attach here

A Role + RoleBinding grants verbs on resources inside one namespace. "User X can edit Deployments in pr-*" is the natural shape — and it's why the OIDC setup can give CI broad rights inside preview namespaces without giving it cluster admin.

quota

Resource quota boundary

Attach a ResourceQuota to a namespace ("this folder gets at most 4 CPU and 8 GiB RAM total") and a runaway PR preview can't starve production workloads on the same nodes.

network

NetworkPolicy default scope

NetworkPolicy objects attach to a namespace. "Pods in pr-123 can talk to each other but not to prod" is a one-object rule. Without namespaces, you'd be matching on labels across the whole cluster.

Lifecycle unit — the one that matters most for deploy-pr Deleting a namespace cascades. Every namespaced object inside it (Deployment, Pod, Service, Secret, ConfigMap, Ingress, PVC…) is garbage-collected by Kubernetes automatically. That's why deploy-pr down <PR> is a one-line tear-down: delete the pr-<N> folder, and the contents go with it. No bookkeeping, no orphans (in the happy path).

3What a namespace is not

Three common misconceptions, three quick correctives. Each of them matters because the wrong mental model leads you to expect the wrong permissions.

Not a security boundary at the kernel/network level (by default) Pods in pr-123 and pr-456 share the same nodes, the same Linux kernel, and (without NetworkPolicy) the same flat pod network. Two namespaces aren't isolated like two VMs are — they're isolated by policy (RBAC, NetworkPolicy, ResourceQuota). True isolation needs a separate cluster, or strict NetworkPolicies plus PodSecurity admission.
Not a hierarchy Namespaces are flat. There's no "sub-namespace" in vanilla Kubernetes. pr-123 isn't inside anything except the cluster itself. (Extensions like Hierarchical Namespace Controller exist but are off by default.) This matters because there's no parent folder whose permissions could "cover" namespace creation — see §4.
Not where every resource lives Some resources are cluster-scoped: they don't belong to any namespace. The list includes Node, PersistentVolume, StorageClass, ClusterRole, ClusterRoleBinding, CustomResourceDefinition — and crucially, Namespace itself. That's the bridge into the next section.

4Cluster-scoped vs namespace-scoped — the punchline

Every Kubernetes resource kind lives in one of two worlds. The world it lives in decides what kind of permission can grant access to it.

Left: things you can sandbox to a folder. Right: things that are the folder structure (or live outside any folder).

Now combine this with one limitation of Kubernetes RBAC: rules can restrict get, update, and delete to specific resource names (e.g. "user can delete Deployment api"), but they cannot restrict create by name pattern. When you're creating something, its name doesn't exist yet to filter on. So this rule is impossible:

# NOT EXPRESSIBLE in standard RBAC
verbs:     ["create"]
resources: ["namespaces"]
resourceNames: ["pr-*"]   # ← no, can't pre-filter creation by name

Which means: granting "create namespaces" necessarily grants the creation of any namespace name. Including kube-system-shadowing names, including names that collide with another team's workspace. That's why it's a privileged verb even when you "only meant" pr-*.

The workarounds This is exactly why the OIDC setup doc's §4 offers two paths: Path A grants the cluster-scoped verb and layers a ValidatingAdmissionPolicy (or Kyverno/OPA) to enforce the pr-* name pattern at admission time — because RBAC alone can't. Path B sidesteps the whole thing by having an admin (or controller) pre-create the namespace, so the workload principal never needs the verb at all.

5The three permission systems stacked under deploy-pr

Now the asymmetry from the original question becomes obvious. When CI runs deploy-pr up <PR>, three independent permission systems check it in sequence:

LayerWhat it decidesExample checks
AWS IAM Can this AWS principal call this AWS API? ecr:PutImage on the image repo · eks:DescribeCluster on the cluster
EKS access entry How does this AWS principal map into the Kubernetes cluster, and at what scope? "Map role/github-deploy-pr to K8s identity, scoped to namespaces pr-*"
Kubernetes RBAC Once inside the cluster as a K8s identity, what verbs on what resources? create deployments in pr-123 · create namespaces at the cluster scope

Two implications follow:

  • Pushing an image to ECR doesn't touch the cluster at all. It's an AWS IAM check against an AWS service. Kubernetes doesn't know it happened. So "can push image" and "can create K8s namespace" are decided by completely different systems and have no reason to track each other.
  • "Deploy a workload into an existing namespace" and "create a new namespace" are both Kubernetes RBAC checks — but on resources from the two different worlds in §4. The first is sandbox-able; the second isn't.
Why local feels different from CI Your laptop's IAM user is probably mapped to a broader EKS access policy (often something like AmazonEKSClusterAdminPolicy), so its K8s identity has the cluster-scoped create namespaces verb by default. The OIDC role for CI is intentionally narrower — that's the whole point of the setup — so it hits the wall the moment --create-namespace tries to fire.

6Back to deploy-pr

With the model in place, every deploy-pr behaviour lines up:

  • Each PR gets a pr-<N> folder. Helm installs the chart's objects into that folder. The chart never has to think about other PRs because the folder gives it its own naming space.
  • deploy-pr down <PR> deletes the folder. Kubernetes garbage-collects every namespaced object inside it (§2). One delete, full tear-down.
  • The §4 Path A / Path B choice in the OIDC doc is not paranoia. It's the only way to reconcile two facts: (a) namespaces are cluster-scoped, (b) RBAC can't pre-filter create by name. You either accept the cluster-scoped verb and gate it with an admission policy, or you keep the principal narrow and pre-create the folder.
  • deploy-pr list works by listing namespaces matching pr-*. That's a cluster-scoped read, which is why the read side of namespaces usually still needs to be granted even in Path B.
One-line summary A namespace is a folder. Putting files into a folder is a permission you can scope to that folder. Creating a folder at the root of the filesystem is a permission you can only scope to the whole filesystem. That's the entire story.
