# Wire deploy-pr CLI to the zuqdev EKS cluster

## Context

The infra foundation is now in place: an EKS cluster in `us-west-2`,
ingress-nginx fronted by an NLB, a wildcard alias `*.preview.zuqdev.com` →
NLB in Route 53, and a Let's Encrypt **prod** wildcard cert
(`*.preview.zuqdev.com`) wired as ingress-nginx's `default-ssl-certificate`.
Verified end-to-end: `https://pr-test.preview.zuqdev.com` returns the
ingress-nginx default 404 with a publicly-trusted cert.

The `deploy-pr` Go CLI on branch `feat/cli-scaffold` is feature-complete —
all units U1–U9 from the original plan have landed (cobra scaffold, config
loader, GitHub PR resolution, ECR auth, Docker buildx, Helm Manager, kube
listing, sticky comments, GoReleaser/CI). The remaining task is purely
**configuration**: tell the CLI which cluster, region, ECR repo, and base
domain to use, and ensure `KUBECONFIG` resolves to the EKS cluster context.

No Go code changes are required for this step. The whole job is editing
`.deploy-pr.yaml` and a small shell-environment + smoke-test sequence.

Two values still need a one-shot AWS lookup the user will run:
- Cluster name: `aws --profile eks eks list-clusters --region us-west-2`
- ECR repo: either reuse an existing one
  (`aws --profile eks ecr describe-repositories --region us-west-2`) or
  create a fresh one (`aws --profile eks ecr create-repository ...`).

## Implementation steps

### Step 1 — Discover/confirm AWS resources

```bash
export AWS_PROFILE=eks
export AWS_REGION=us-west-2

# Cluster name
aws eks list-clusters --region us-west-2

# ECR — list existing
aws ecr describe-repositories --region us-west-2 \
  --query 'repositories[].{Name:repositoryName,URI:repositoryUri}' \
  --output table

# If no suitable ECR repo exists, create one (name it after the app you'll deploy):
# aws ecr create-repository --region us-west-2 --repository-name <app-name> \
#   --image-scanning-configuration scanOnPush=true
```

Capture the `URI` value verbatim — that's `ecr_repo_uri`.

### Step 2 — Make sure kubeconfig points at the EKS cluster

```bash
aws eks update-kubeconfig --name <cluster-name> --region us-west-2 --profile eks
kubectl config current-context     # should now show the EKS cluster
kubectl get nodes                  # smoke test: should list ready nodes
```

`deploy-pr` does not pass `--profile` to AWS calls or `--kubeconfig` to kube
calls; it relies on the env. So the shell that runs `deploy-pr` must have
`AWS_PROFILE=eks` exported (or those credentials in the default chain) and
the kubeconfig current-context pointing at this cluster.

### Step 3 — Edit `.deploy-pr.yaml`

File: `C:\Users\aguia\Dev\pessoal\deploy-pr\.deploy-pr.yaml`

Uncomment and fill `ecr_repo_uri`, `cluster_name`, `base_domain`. Change
`region` from `us-east-1` to `us-west-2`. Final shape:

```yaml
# (comments preserved as in the original sample)

ecr_repo_uri: <account-id>.dkr.ecr.us-west-2.amazonaws.com/<repo-name>
region: us-west-2
cluster_name: <cluster-name from step 1>
base_domain: preview.zuqdev.com

chart_path: charts/preview
namespace:
  prefix: pr-
timeout: 10m
log_format: text
```

Leave `repo:` commented so the CLI auto-detects from `git remote get-url
origin` of whichever app repo the operator is running it from. The deploy-pr
repo's own `.deploy-pr.yaml` is **just a template** — the operator typically
copies it into the *target app's* repo, but the values above (cluster, ECR,
domain) are reusable across all apps that share this preview cluster, so
keeping them in deploy-pr's repo as defaults documents the production
configuration.

### Step 4 — Build the binary

```bash
cd C:\Users\aguia\Dev\pessoal\deploy-pr
go build -o bin/deploy-pr .
./bin/deploy-pr version
```

(Optional: `go install .` to drop `deploy-pr` on `$PATH`.)

### Step 5 — Smoke test in dry-run mode

Pick any open PR number from a repo with a Dockerfile to test resolution
without provisioning anything:

```bash
cd <some-repo-with-open-PR-and-Dockerfile>
cp <path-to>/deploy-pr/.deploy-pr.yaml .   # or symlink, or use --config

DEPLOY_PR_BASE_DOMAIN=preview.zuqdev.com \
  /path/to/deploy-pr up <PR#> --dry-run -v
```

Expect: PR metadata resolved, image tag computed, target host
`pr-<N>.preview.zuqdev.com`, target namespace `pr-<N>`, no AWS/Helm calls
(the `--dry-run` flag at `cmd/up.go:18-22` short-circuits before the build).

### Step 6 — End-to-end smoke test (real `up`)

This actually builds, pushes, and installs. Needs the target repo to have
a working Dockerfile with an HTTP server on port 8080 (the chart's default
`containerPort`).

```bash
deploy-pr up <PR#> -v
# Watch the logs: docker buildx → ECR push → helm install
# Final line should print the URL: https://pr-<N>.preview.zuqdev.com
```

Verify:

```bash
kubectl get ns pr-<N>
kubectl -n pr-<N> get all,ingress
curl -I https://pr-<N>.preview.zuqdev.com
# Expect 200 (or whatever the app returns) on TLS chain that already validates.
```

Then teardown:

```bash
deploy-pr down <PR#> -v
kubectl get ns pr-<N>     # should report NotFound
```

## Out of scope (deliberately deferred)

- ExternalDNS install — the wildcard CNAME covers every hostname; only
  worth installing if we later want per-host record visibility or DNS-01
  per-host certs. The chart already emits the right annotation for when
  it is installed.
- IRSA for the *deploy-pr operator role* — we configured IRSA for
  cert-manager, but `deploy-pr` itself just needs a developer/CI principal
  with `eks:DescribeCluster`, ECR push, and kubeconfig access. The
  GitHub-Actions reference workflow (`.github/workflows/preview.yml`) and
  `docs/aws-oidc-setup.md` already cover the CI side.
- Per-PR secrets / app config — the chart accepts env values but not
  Secret provisioning; the operator handles that out-of-band.
