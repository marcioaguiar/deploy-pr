How aws, kubectl, and helm connect to your account — and how to keep your laptop safe

Three command-line tools, one chain of trust. aws talks to AWS, kubectl talks to Kubernetes, and helm talks through kubectl. Once you see the chain, security becomes obvious: protect the first link and everything downstream follows.

1The cast: three CLIs, three jobs

You'll see all three installed side-by-side on most engineers' laptops. They look similar (terminal commands, YAML output) but they each talk to a different system.

cloud

aws

The AWS CLI. Talks to AWS APIs: S3, IAM, EKS, EC2, etc. Authenticates with an AWS identity (access key, SSO, or OIDC token).

kubernetes

kubectl

The Kubernetes CLI. Talks to a Kubernetes API server: list pods, apply YAML, view logs. Needs to know which cluster and who you are.

packaging

helm

A Kubernetes package manager. Renders templates into Kubernetes YAML, then asks kubectl's library to apply it. Helm does not talk to AWS at all.

One-line mental model

aws is your passport. kubectl is the plane ticket that the passport gets you into. helm is the luggage you check once you're already on the plane.

3How aws connects to your account

The AWS CLI is the foundation. Every other tool here gets its identity from it (directly or indirectly). When you run aws s3 ls, the CLI does four things:

  1. Looks up which identity to use (environment variables, then ~/.aws/credentials, then ~/.aws/config for SSO/profiles, then EC2/ECS metadata if it's running on AWS).
  2. Gets credentials for that identity. Either a static access key, or a short-lived token from SSO/STS/OIDC.
  3. Signs the request with SigV4 — a cryptographic signature that proves you hold the credentials, without sending the secret over the wire.
  4. Sends the HTTPS request to the right AWS service endpoint (e.g. s3.us-east-1.amazonaws.com).

The three common identity flavors

FlavorWhat's on your laptopRisk if leaked
Static access key
AKIA…		 A long-lived secret in ~/.aws/credentials. Works until rotated. High. Attacker has your AWS identity until someone notices and revokes the key.
SSO / IAM Identity Center A short-lived token cached in ~/.aws/sso/cache/. You re-login via browser every few hours. Medium. Tokens expire (typically 8–12 h). Stolen token is dangerous until expiry.
OIDC / web identity (used in CI) Nothing persistent. CI presents a signed JWT and gets a 15-minute STS token. Low. Tokens are minutes-long and tied to a specific GitHub repo/branch.
Beginner recommendation Prefer SSO on your laptop, and OIDC for CI. Static access keys should be a last resort — and never committed anywhere.

4How kubectl connects to the cluster (via AWS)

Kubernetes itself doesn't know what an AWS user is. It only understands its own kinds of identities: client certificates, service-account tokens, or generic bearer tokens. On EKS (AWS's hosted Kubernetes), the trick that bridges the gap is in your ~/.kube/config file:

users:
- name: arn:aws:eks:us-east-1:123456789012:cluster/dev
  user:
    exec:
      apiVersion: client.authentication.k8s.io/v1beta1
      command: aws
      args:
        - --region
        - us-east-1
        - eks
        - get-token
        - --cluster-name
        - dev

That exec: block is the key. Every time kubectl needs to call the API server, it shells out to aws eks get-token. The aws CLI signs a request using your AWS identity and returns a short-lived bearer token (~15 minutes). kubectl puts that token in the Authorization header and sends its request to the EKS API server.

Why this matters for security

Your laptop never stores a long-lived Kubernetes credential. The only secret is your AWS identity. Revoke that, and access to every EKS cluster goes away in 15 minutes — no certificate rotation, no manual cleanup.

Setting this up is one command:

aws eks update-kubeconfig --name dev --region us-east-1

That writes the cluster's address, its CA certificate, and the exec: block above into ~/.kube/config. From then on, kubectl get pods "just works."

What the API server does on the other end

  1. Receives the bearer token from kubectl.
  2. Asks AWS STS: "Whose token is this?" → gets back an AWS IAM ARN.
  3. Looks up that ARN in the aws-auth ConfigMap (or EKS access entries) to map it to a Kubernetes user/group.
  4. Runs RBAC: is this Kubernetes user allowed to do what they're asking?

5Where helm fits — it borrows kubectl's connection

This is the part that surprises most beginners: Helm has no concept of "logging in." It does not have its own credentials. It does not talk to AWS. It does not even open its own HTTP connection to Kubernetes most of the time.

When you run helm install my-app ./chart, here's what actually happens:

  1. Helm reads your chart's templates and values.yaml.
  2. It renders them into plain Kubernetes YAML in memory.
  3. It loads the same ~/.kube/config that kubectl uses, using the official Kubernetes Go client library.
  4. It calls Kubernetes APIs (often kubectl apply-equivalent operations) to create the objects.
  5. It stores a record of what it installed — the release — as a Secret inside the namespace it deployed to.
The key insight Anything kubectl can do, helm can do — and only what kubectl can do. If your AWS user is not allowed to create Deployments in namespace prod, helm cannot create them either. Helm gives you templating and release tracking. It does not give you new permissions.

What about Helm repositories?

Helm does talk to the network for one thing: downloading charts. helm repo add ... and helm pull ... reach out to chart registries (HTTPS or OCI). These are read-only and usually public; they don't need AWS credentials. If you host charts in a private ECR or S3 bucket, then yes — at that point Helm reuses your AWS identity through a plugin like helm-s3 or aws ecr get-login-password.

7Keeping your laptop secure — a practical checklist

The whole chain rests on what's in your home directory. Protect those few files and everything downstream is safe.

  • Prefer SSO over static keys. If you must use access keys, scope them tightly and rotate them every 90 days.
  • Never put credentials in your shell history or repo. No export AWS_SECRET_ACCESS_KEY=... in .bashrc. No .env with keys committed.
  • Check file permissions. ~/.aws/credentials and ~/.kube/config should be chmod 600 (read/write for you only).
  • Encrypt your disk. FileVault on macOS, LUKS on Linux. If your laptop is stolen, this is the only thing standing between the thief and your credentials.
  • Use MFA on the AWS account. Required for both console and CLI when possible. SSO enforces this naturally.
  • Don't share kubeconfigs. If a teammate needs cluster access, give them their own AWS identity and let them run aws eks update-kubeconfig. Sharing a kubeconfig file means they inherit your AWS identity through the exec: block.
  • Watch what you curl | bash. Anything that runs as your user can read ~/.aws/credentials. Install aws, kubectl, helm from official sources or your package manager.
  • Use separate AWS profiles per environment. A dev profile and a prod profile in ~/.aws/config, and export AWS_PROFILE=dev in your shell. Makes "oops, wrong cluster" much harder.
  • Audit periodically. aws iam list-access-keys and kubectl config get-contexts show you what your laptop currently believes it can do.
If you lose your laptop Two phone calls. (1) Your AWS admin revokes your access keys / signs you out of SSO. (2) Your IT helpdesk locks the device. Because kubectl tokens are minutes-long and derived from AWS, step (1) cuts off cluster access automatically — you don't need to chase down every kubeconfig.

8How easy is the setup, really?

Genuinely easy. On a fresh laptop, you're typically 10 minutes from your first helm install:

# 1. install the tools (Homebrew on macOS shown; use apt/winget elsewhere)
brew install awscli kubectl helm

# 2. log into AWS — pick ONE
aws configure sso                  # recommended
# or
aws configure                      # static keys (legacy)

# 3. point kubectl at your EKS cluster
aws eks update-kubeconfig --name dev --region us-east-1

# 4. verify
kubectl get nodes
helm list -A

That's it. There is no separate "helm login," no separate "kubectl login" — step 3 wires kubectl to AWS via the exec: trick, and helm picks it up automatically.

The whole point One identity (your AWS user), one short-lived token mechanism, three CLIs that all benefit from it. Protect the AWS identity well and the rest of the chain takes care of itself.
