Why "create namespaces" is a privileged verb — through four threat models

The risk isn't that creating a folder is dangerous. The risk is that the verb create namespaces is unbounded by design — and an unbounded capability has very different consequences depending on who holds it. Same verb, four threat models, four different answers.

0The kernel of the risk

People often ask "is granting create namespaces dangerous?" That's the wrong question. The right one is: "who holds the credential, and what's the worst thing that credential can be coerced into doing?"

Analogy

A master key to a building is exactly as risky as the person carrying it. The key itself is just brass. The risk is the combination of (a) what doors it opens, (b) who has it, and (c) how easily it can be taken or coerced. A trusted janitor with the master key is fine. A janitor whose pocket gets picked nightly is a problem. The same key, two completely different risk profiles.

The same verb sits at vastly different points on the risk curve depending on context. Sections §3–§6 walk through four of those contexts, in increasing order of risk.

1What the verb actually grants

Before the threat models, the capability needs to be clear. From the namespaces explainer §4: Kubernetes RBAC cannot pre-filter create by resource name. So this rule:

apiGroups: [""]
resources: ["namespaces"]
verbs:     ["create"]

…is equivalent to "can create a namespace with any name whatsoever". Concretely, a holder of this verb can create:

Expected names

  • pr-123, pr-456 — what you actually wanted

Unexpected names

  • prod, staging, payments — collisions with real workloads
  • kube-system-shadow, kube-public-2 — names that controllers may treat specially
  • default if it was previously deleted
  • 10,000 namespaces in a loop — denial of service via control-plane load
You can put a guardrail on top — but RBAC isn't it A ValidatingAdmissionPolicy, Kyverno, OPA Gatekeeper, or a mutating webhook can enforce "namespace names must match pr-*" at admission time. That guardrail is what turns an unbounded RBAC verb into a bounded effective capability. Without it, create namespaces is intrinsically global.

2Threat model 1 — your laptop, your own dev cluster

Risk: very low Recommended: grant freely

You're the only principal. The cluster is disposable. The "attacker" is your own typo. The blast radius of misuse is "I deleted a namespace I didn't mean to" — which is what kubectl create is for, in reverse.

In this world, cluster-admin on your laptop is fine, and create namespaces is a non-event. This is why most local dev clusters (kind, minikube, k3d) hand out admin credentials by default and nobody complains.

Why deploy-pr up from your laptop "just works" Your local IAM user is almost certainly mapped to a broad EKS access policy (commonly AmazonEKSClusterAdminPolicy), which carries create namespaces implicitly. You never had to think about it because the verb came as part of a bundle you were already trusted with.

3Threat model 2 — your laptop, a shared cluster

Risk: moderate Recommended: grant, but pair with admission policy

Now your laptop credential is one of many that touch the same cluster. Other teams have prod, payments, billing namespaces. The cluster has shared infrastructure controllers watching for new namespaces. Three concrete risks emerge:

Blast radius if your laptop is compromised

A stolen kubeconfig with create namespaces + cluster-wide workload verbs lets an attacker plant workloads anywhere in the cluster — not just in pr-*. They create pr-attacker, deploy a crypto miner, and your deploy-pr list command (which filters by the managed-by=deploy-pr label) won't even surface it. The pods still run, the bill still accrues.

Accidental collision with shared infra

A typo like kube-systen can confuse cluster controllers in subtle ways. Recreating default after someone deleted it (with non-standard configuration) can break service-account injection for the whole cluster. These aren't malicious — but the blast radius of "oops" scales with how many other tenants exist.

Resource and cost amplification

Every namespace creates default ServiceAccounts, optionally default Secrets, and triggers re-evaluation of every cluster-wide controller's namespace watch. A leaked credential running for i in {1..10000}; do kubectl create ns x-$i; done is a control-plane DoS vector — etcd writes, controller queues, audit log churn.

Audit trail noise

When 20 developers share a cluster and all hold create namespaces via their personal IAM users, the audit log for "who created weird-namespace-xyz?" is fine — but the audit log for "who has historically been able to do this?" is "everyone." That makes post-incident scoping harder.

Mitigation Keep the verb, but layer an admission policy that restricts namespace names per principal or per group. E.g. "principals in group deploy-pr may only create namespaces matching pr-*." Kubernetes RBAC can't do this; ValidatingAdmissionPolicy (1.30+), Kyverno, or OPA Gatekeeper can.

4Threat model 3 — a cluster with namespace-bound admission controllers

Risk: high (privilege escalation) Recommended: never grant unconditionally

This is where the risk crosses from "annoying" to "actual security incident." Many production clusters layer mutating admission webhooks that fire on namespace creation. Common patterns:

  • Auto-attach a default ResourceQuota and LimitRange.
  • Auto-attach a default NetworkPolicy.
  • Auto-bind the namespace's creator to an admin RoleBinding inside that namespace.

That last one — common in self-service-namespace controllers like Capsule, Hierarchical Namespace Controller, vcluster, or homegrown operators — turns create namespaces into create your own tenancy and become its admin. Which means any narrower RBAC restriction on pr-* is bypassable: just create evil-1 and you're admin there.

When the cluster auto-promotes namespace creators, create namespaces is effectively cluster-admin in any tenancy you invent.

Detection is also harder here An audit log entry saying "principal X created namespace Y" looks identical whether Y is a legitimate PR or an attacker tenancy. You have to correlate with subsequent workload activity to tell them apart — and most teams don't have that pipeline wired up.
How to defuse this Either (a) don't run namespace-auto-admin webhooks in clusters where untrusted-ish principals hold create namespaces, or (b) make the webhook itself check the namespace name against a per-principal allowlist before issuing the admin binding. The second is what mature self-service controllers (like Capsule's tenant scoping) actually do.

5Threat model 4 — GitHub Actions on a pull_request trigger

Risk: maximum Recommended: Path B if remotely feasible

This is the threat model the OIDC setup doc actually cares about, and the reason §4 of that doc exists at all. A GitHub Actions principal isn't a person — it's whatever code happens to be checked out at the time the workflow runs.

The crucial difference

When you grant your laptop a permission, you're trusting yourself. When you grant a pull_request-triggered GitHub Actions workflow a permission, you're trusting any code anyone ever opens a PR with. Those are not the same trust boundary. The PR author is, in the worst case, an internet stranger writing exploitative code.

Combine that trust model with create namespaces and the attacks compound:

  • Cluster shadowing. Malicious PR triggers a workflow that creates kube-system-2 or shadow-names variations of real namespaces, then schedules privileged workloads inside. Even without auto-admin webhooks, the namespace name alone can interact with admission policies or controllers that key off names.
  • DoS via namespace flood. The PR's CI script runs for i in $(seq 1 10000); kubectl create ns x-$i. Etcd writes spike, controllers queue, audit log explodes, real PR previews fail to deploy because the control plane is saturated.
  • Lateral movement via §4's privilege escalation. If the cluster runs any namespace-creator-auto-admin webhook, the malicious PR escapes the pr-* sandbox in one step (see §4).
  • Long-lived steady state. The OIDC token expires in an hour, but namespaces created during that hour persist until something deletes them. A single malicious run can leave permanent footprint.
Why the OIDC trust policy locks down to pull_request + one repo Recall §2 of the OIDC ELI5 doc: the trust policy pins sub to one specific repo and one specific event. That narrowing is the only thing standing between "PR author" and "anyone on GitHub." A wildcard repo:owner/*:* would let any workflow in any repo (including freshly-forked ones) assume the role. With create namespaces on the other side of that gate, a misconfigured trust policy is game over.
The two production-grade options

Both are documented in aws-oidc-setup.md §4:

  • Path A — grant the verb, but bind a ValidatingAdmissionPolicy (or Kyverno/OPA) restricting namespace names to pr-* for this group. RBAC + admission policy together = the bounded capability RBAC alone can't express.
  • Path B — don't grant the verb at all. Have an admin or controller pre-create pr-<N> on PR open, and run deploy-pr up <N> --create-namespace=false. The CI principal stays strictly namespace-scoped with no cluster-scoped verbs whatsoever.

Path B is the safer default for any cluster where untrusted PR code might run. Path A is acceptable when the admission policy is in place and audited.

6Decision matrix

Same verb, four threat models, four answers:

Threat model Who holds the credential Worst case Grant create namespaces?
TM1 — Laptop, dev cluster You Typo, recreate it Yes, no guardrails needed
TM2 — Laptop, shared cluster You + 20 colleagues Collision, accidental DoS, lost credential lateral movement Yes, pair with admission policy and audit
TM3 — Cluster with auto-admin webhooks Anyone with the verb Privilege escalation to admin of attacker-named namespace Only if webhook itself restricts by name
TM4 — GitHub Actions pull_request Any PR author, including forks Shadow namespaces, control-plane DoS, sandbox escape Prefer Path B; if Path A, admission policy is mandatory
The portable rule Capability + threat model + guardrails = effective risk. create namespaces is identical capability across all four rows. What changes is who's holding it and what else exists to bound it. The verb is never "safe" or "unsafe" in the abstract — it's safe relative to a threat model.
